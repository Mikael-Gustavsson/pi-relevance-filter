# A/B benchmark: Pi vanilla vs Pi + relevance filter

Measured with version 0.1 ("Pi NPU context filter"), which ran on the NPU only and used the old names
(`PI_NPU_*`, `[NPU filter]`). Pi 1.5.0, OpenVINO 2026.4.1, frontier model `github-copilot/claude-sonnet-5.5`.
The data is synthetic, generated by the service's case generator (held-out seed 7). The host is described in the
service's [environment](https://github.com/Mikael-Gustavsson/relevance-filter/blob/main/docs/environment.md).
Offline filter quality and per-device latency are in the service's
[benchmark report](https://github.com/Mikael-Gustavsson/relevance-filter/blob/main/docs/benchmark.md).

## Method

`scripts/ab-benchmark.py --repeats 2`, raw metrics: [`benchmarks/results/ab-v1-final.json`](../benchmarks/results/ab-v1-final.json).

Identical prompts, model, case files and extension in both variants. Only the enable switch differs. Every run
uses a fresh temp workspace holding only the tool-output file. Success means all expected keywords appear in Pi's
final answer. Medians over 2 runs. Order alternates between repeats.

## Observations

* **Correctness unchanged:** 16/16 correct in both variants.
* **Fewer turns.** Vanilla Pi's bash keeps only the last 50 KB / 2000 lines, so it greps for more. With the filter, the frontier gets
  relevant chunks from the *whole* output (via `details.fullOutputPath`) and usually answers after the first tool call.
* In the logs case, the filtered result (15 k tokens) is *larger* than vanilla's truncated tail (13.7 k). The saving comes from
  fewer follow-up turns. Cost per run is therefore about equal there.
* In rg, the frontier model called `get_raw_tool_result` once to check context, so the recovery path is used in practice.
* NPU overhead (0.4–2.2 s) is below the wall-clock saved from fewer turns in 3 of 4 cases.

### Run v0: a bug the A/B caught

[`benchmarks/results/ab-v0-query-tail-bug.*`](../benchmarks/results/): the first A/B run trimmed long tasks to their
**last** 48 tokens. In the rg case the query became "...Start by running exactly: cat rg-retry-results.txt", and the
filter kept 1/97 chunks. The frontier model recovered via `get_raw_tool_result` and still answered correctly. The fix
keeps the head (64 tokens), where the goal is usually stated. The tables above are from run v1, after the fix.

## Jev comparison

Not run. Real Jev is reachable only through the TypeSafe classifier API (`TYPESAFE_API_KEY`, see Pi's
`examples/extensions/jev-router.ts`), and no credential is configured on the reference machine.
`ab-benchmark.py` can take a third variant once a Jev-backed filter exists.

## Limitations

* All cases are synthetic, and there are only 4 task types.
* Large full-output files (> 50 KB) exceed the 500 ms target on every device. Lower
  `PI_RELEVANCE_FILTER_MAX_INPUT_CHARS` to cap latency, at the cost of falling back to Pi's tail truncation.
  On the CPU the service's own recommendation (100 KB) already does this.

## Reproduce

```powershell
# in the relevance-filter checkout
python benchmarks\generate_cases.py
python -m relevance_filter --device NPU          # keep running

# in this repository (cases default to ..\relevance-filter\benchmarks\cases)
python scripts\ab-benchmark.py --device NPU --repeats 2 [--cases-dir <relevance-filter>\benchmarks\cases]
```

The script needs a Pi login. It writes metrics only (no tool content) to `benchmarks/results/ab-<timestamp>.json`.
